## 1. チャットパネルの使い方

### パネルの開き方

- 左アクティビティバーの **ロボットアイコン** をクリック
- または `Ctrl+Shift+P` → `Local LLM: Open Chat`

### パネルの構成

```
┌─────────────────────────────────────────────┐
│ [gemma4 ▼]  [＋] [⏱] [⚙]                 │ ← ① ツールバー
├─────────────────────────────────────────────┤
│                                             │
│  You: バグを探して                           │ ← ② 会話エリア（マークダウン描画）
│                                             │
│  ● ● ●  ← (応答待ちアニメーション)           │
│                                             │
│  ▶ Thinking…  ← (折り畳み思考過程)          │
│                                             │
│  Assistant: ...（マークダウン形式で表示）     │
│  ┌─ ⟳ read_file { "path": "src/..." } ───┐ │ ← ③ ツール実行ログ（実行中はスピナー）
│  │ (ツール結果...)                        │ │    結果到着でスピナーが消える
│  └────────────────────────────────────────┘ │
│  ┌─────────────────────────────────────────┐ │
│  │ 🔑 Permission Request                  │ │ ← ④ 権限確認（必要時のみ）
│  │  Edit: src/main.py  ▶ View changes     │ │
│  │  [Yes (once)] [Always Yes (session)] [No]│ │
│  └─────────────────────────────────────────┘ │
│  ┌─────────────────────────────────────────┐ │
│  │ 📋 Execution Plan                      │ │ ← ⑤ 計画承認（repo-map モード時）
│  │  1. read_file ...                      │ │
│  │  [Approve] [Cancel]                    │ │
│  └─────────────────────────────────────────┘ │
│ [@ src/main.ts ✕] [✂ foo.ts:5-10 ✕]      │ ← ⑥ 添付チップ
├─────────────────────────────────────────────┤
│ [📎][／] [main.py]  ● [Agent:Loop][🔒 Ask][○]↑│ ← ⑦ 入力欄
│      ↑コマンド ↑アクティブファイル ↑Agentモード ↑権限モード ↑トークン
└─────────────────────────────────────────────┘
```

> **入力エリアのサイズ:** テキスト量に応じて高さが自動拡張し、パネル高さの約 45% まで伸びます。

> **アクティブファイル表示:** `／` ボタン右隣に、現在エディターで開いているファイル名（例: `main.py`）が表示されます。ファイル名左の **書類マーク＋目アイコン** をクリックすると、そのファイルをコンテキストに含めるかどうかをトグルできます（目に斜線が入ると除外）。

### キーボード操作

| 操作 | キー |
|---|---|
| メッセージ送信 | `Enter` |
| 改行の挿入 | `Shift+Enter` |
| スラッシュ/メンションメニューを選択 | `↑` / `↓` |
| 選択を確定 | `Enter` |
| メニューを閉じる | `Esc` |
| エージェント停止 | 入力欄右の **⏹ Stop** ボタン（500ms 後に表示） |

### 応答待ちインジケーター

LLM の応答待ちの間、会話エリアにスピナー（`Waiting for LLM response…`）が表示されます。メッセージ送信直後・各ツール結果の後・プラン承認後・ツール実行許可後に表示され、最初のコンテンツやツール呼び出しが届くと自動的に消えます。

### エージェントの停止

入力欄右の **⏹ Stop** ボタンをクリックすると、進行中の生成・ツール実行・権限待ちをすべて中断します。

- ダブルクリック誤操作を防ぐため、送信後 500ms は Stop ボタンが表示されません
- Stop 押下後、UI は即座に通常状態に戻ります

## 2. モデルの切り替え

ツールバー左端のドロップダウンから現在 Ollama で利用可能なモデルに即座に切り替えられます。

デフォルトモデルは `gemma4:26b-a4b-it-q4_K_M`（1モデルのみで全機能を試せます）。

> **モデルの記憶:** 選択したモデルはワークスペース単位で記憶され、次回起動時に自動的に復元されます。

### タスク別モデルの設定

```jsonc
"localLlm.models.chat":       "gemma4:26b-a4b-it-q4_K_M",
"localLlm.models.vision":     "gemma4:26b-a4b-it-q4_K_M",
"localLlm.models.translate":  "gemma4:26b-a4b-it-q4_K_M",
"localLlm.models.compaction": "gemma4:26b-a4b-it-q4_K_M"
```

## 3. スラッシュコマンド / スキル

入力欄に `/` を入力すると、使用可能なコマンドがフローティングメニューで表示されます（Claude Code スタイル）。`／` ボタンでも開けます。

### 組み込みコマンド

| コマンド | バッジ | 説明 |
|---|---|---|
| `/compact` | built-in | 会話履歴を要約して圧縮 |
| `/new` | built-in | 新しいセッションを開始 |
| `/history` | built-in | セッション履歴パネルを開く |
| `/rag` | built-in | RAG インデックスを再構築 |
| `/help` | built-in | 利用可能なコマンド一覧を表示 |

### Git コマンド

| コマンド | バッジ | 説明 |
|---|---|---|
| `/git:status` | git | git status を即座に実行 |
| `/git:diff` | git | staged/unstaged の差分を即座に表示 |
| `/git:log` | git | 最近のコミット履歴を即座に表示 |
| `/git:commit` | git | 変更をレビューしてコミット |
| `/git:branch` | git | ブランチ一覧を即座に表示 |
| `/git:stash` | git | stash の一覧・操作 |

> **Git コマンドは選択した時点で即座に送信されます**（入力欄への挿入は行いません）。

### カスタムスキルの追加

```jsonc
"localLlm.skills": [
  {
    "command": "review",
    "description": "コードレビューを依頼する",
    "prompt": "このコードをレビューしてください。バグ・可読性・パフォーマンスの観点でフィードバックをお願いします。"
  }
]
```

## 4. ファイル・画像の添付

### テキストファイル

- 入力欄へ **ドラッグ&ドロップ**
- **📎 ボタン** からファイル選択

### 画像（Vision モデル自動切替）

画像ファイル（`.png` `.jpg` `.gif` `.webp` `.bmp`）を添付すると自動認識されます。  
画像が含まれるメッセージでは、`localLlm.models.vision` に設定したモデルへ自動切替します。  
`models.vision` が `models.chat` と同じ場合はそのまま使用されます（マルチモーダル対応モデルであれば1つで動作します）。

> 専用のVisionモデル（例: `llava`）を使いたい場合は設定で個別に指定してください。

## 5. @ファイルメンション

入力欄で `@` に続けてファイル名を入力すると、ワークスペース内のファイルを素早く参照できます。

```
@main.ts → ファイルピッカーが表示 → 選択するとチップに変換
```

### 操作方法

1. 入力欄に `@` を入力（またはファイル名の先頭文字も入力可）
2. フローティングメニューにファイルが絞り込み表示される
3. `↑` / `↓` で選択、`Enter` または クリックで確定
4. 確定すると入力欄に `@ ファイルパス ✕` チップが追加される
5. メッセージ送信時に、ファイルの内容がコンテキストとして自動添付される

> 複数ファイルのメンションも可能です。チップの `✕` をクリックすると削除できます。

---

## 6. エディター選択テキストの自動取り込み

VSCode エディターでコードを選択すると、入力欄に `✂ ファイル名:行番号 ✕` チップが自動的に追加されます。

メッセージ送信時に選択したコードブロックがコンテキストとして含まれるため、「このコードを説明して」「このバグを修正して」といった操作が簡単になります。

- 選択を解除するとチップは自動削除されます
- `✕` をクリックして手動で削除することもできます

## 7. エージェントモードの違い

### エージェントモードの切替ボタン

入力欄の **Agent モードボタン**（`Agent: Loop` など）をクリックすると、7つのモードをその場で切替できます。設定を変更する必要はありません。

| 表示 | モード | 用途 |
|---|---|---|
| `Auto` | auto | メッセージ内容を自動判定して適切なモードへ転送（**デフォルト**） |
| `Chat` | chat | 会話・質問・壁打ち専用。ツールなし、シンプルなQ&A |
| `Agent: Loop` | standard | 通常のエージェントループ |
| `Agent: Debug` | debug | バグ調査専用。Localize→Repair→Validate の3フェーズ |
| `Agent: Plan` | repo-map-plan | Repo Map → 計画 → 承認 → ステップ別実行 |
| `Agent: Loop+` | repo-map-loop | 計画→実行→エラー修正のPDCAサイクル（最大5回） |
| `Agent: ReAct` | react | Tool Calling非対応モデル向けテキストパターン |

---

### Auto（自動判定）

メッセージ内容のキーワードを解析し、最適なモードへ自動転送します。追加のLLM呼び出しはなく、レイテンシの増加はありません。

| 判定条件 | 転送先 |
|---|---|
| bug / error / broken / not working / バグ / 動かない | Debug（3フェーズ） |
| implement / refactor / 実装 / 機能追加 | Plan |
| what is / explain / とは / 教えて + ファイル参照なし | Chat |
| 上記以外 | Agent Loop |

実行開始時に `*[Auto → Debug]*` のような1行が表示されるため、どのモードが選ばれたかを確認できます。判定が外れた場合はモードボタンで手動切替してください。

---

### Chat（純会話）

ツールを一切使わず、シンプルな1回のLLM呼び出しで応答します。

- コードに関係のない質問・説明・アイデア整理・壁打ちに最適
- system promptが「You are a helpful assistant.」のみになるため、ツールルールのノイズがない
- 画像入力（Vision）も使用可能

---

### Agent Loop（デフォルト）

モデルが自律的にツールを呼び出しながら目標に向かって動き続けるモード。最大 20 ターン。

**利用可能なツール:**

| ツール | 説明 | 権限確認 |
|---|---|---|
| `read_file` | ファイルの読み取り（**行番号付きで出力**）。`start_line`/`end_line` で範囲指定可 | なし |
| `get_file_outline` | ファイルの**構造のみ**取得（クラス・メソッド名と行番号）。全文を読まずに場所を特定できる | なし |
| `write_file` | ファイルの書き込み・作成 | **あり（diff 表示付き）** |
| `edit_file` | 既存ファイルの文字列置換（完全一致） | **あり（diff 表示付き）** |
| `replace_lines` | 行番号指定での範囲置換（より確実） | **あり（diff 表示付き）** |
| `glob_search` | ファイルパターン検索 | なし |
| `grep_search` | ファイル内容の正規表現検索（デフォルト大文字小文字区別あり） | なし |
| `run_terminal` | シェルコマンドの実行 | **あり** |
| `ask_user` | ユーザーへの質問（選択肢 or 自由入力） | なし |
| `web_search` | Web 検索（DuckDuckGo） | なし |
| `rag_search` | RAG インデックスの検索 | なし |
| `git` | Git 操作（安全なコマンドのみ） | なし |

> **`get_file_outline` の使いどころ:** バグの場所を探すとき、まず `get_file_outline` でクラス・メソッドと行番号を確認し、次に `read_file(start_line, end_line)` で該当箇所だけ読むことで、コンテキストの無駄遣いを防げます。

> **`edit_file` と `replace_lines` の使い分け:**  
> `read_file` で行番号を確認してから `replace_lines(path, 10, 20, 新しい内容)` で置換するのが最も確実です。`edit_file` は完全一致が必要なため、型アノテーションやコメントの有無でミスマッチが起きることがあります。`edit_file` が「String not found」で失敗した場合は即座に `replace_lines` へ切り替えます。

> **ツール使用のヒント:** エージェントは作業前に `glob_search` でプロジェクト構造を把握し、`read_file` でファイルを確認してから編集を行います。複数ファイルを扱うタスクでは、最初にファイルリストを計画してから作成を始めます。

### シェルの種類

- **Windows:** PowerShell（`Get-ChildItem`, `Get-Date`, `Select-String` 等を使用）
- **macOS / Linux:** bash

> Windows では `ls`, `find`, `grep`, `cat` などの bash コマンドは動作しません。エージェントはシステムプロンプトで PowerShell コマンドを使うよう指示されています。

### Repo Map & Plan

リポジトリ全体を俯瞰してから計画・実行するモード（単発）。

**流れ:**

1. ワークスペースのファイルツリーを自動スキャン（深さ 3 まで）。各ソースファイルからはクラス・関数・型などのシンボルも抽出（Aider スタイルのリポジトリマップ）。**タスク文中で名指しされたファイルは `get_file_outline` の結果（メソッド名＋行番号）も添付**され、コードを読まない誤プランを防ぎます
2. リポジトリマップを参照しながら実行計画を立案（タスク規模に応じて 1〜10 ステップ、最大 3 回自動リトライ）
3. チャット内の **計画承認ブロック** でユーザーが承認
4. 承認後、**各ステップを独立した AgentLoop として順番に実行**（`think:false`）。進捗は `[Step N/M]` バナーで表示

**ステップ実行の制御機構:**

| 機構 | 動作 |
|---|---|
| 完了ゲート | 「修正/実装」系のステップは書き込みツールが実行されるまで完了と認めず、1回まで再試行を促す |
| `STEP MISMATCH:` | 調査の結果プランの前提が誤りと判明した場合の正規の出口。残りステップを中断し、発見内容を入力にして再計画（誤った前提の編集を強制しない） |
| `STEP SKIP:` | ステップの作業が既に完了済みの場合の出口（要・調査ツール1回以上）。エラー扱いせず次のステップへ |
| 無行動/空応答ガード | ツール呼び出しゼロ・出力ゼロのまま終わる生成を検知して1回再試行 |
| エラー集計の正規化 | ガードレール案内（READ LOOP等）は集計から除外。一時的な構文エラーは最終状態が健全なら帳消し |

**ステップ単位の実行例:**

```
📋 EXECUTION PLAN
  1. Edit src/widget.py: fix dropEvent handler in ImageSlot
  2. Create tests/test_widget.py: add drag-and-drop unit tests
  3. Run pytest to verify the fix
  [Approve]  [Cancel]

  [Step 1/3] Edit src/widget.py: fix dropEvent handler in ImageSlot
  ⟳ read_file { "path": "src/widget.py", ... }
  ⟳ edit_file { ... }
  (完了)

  [Step 2/3] Create tests/test_widget.py: ...
  ⟳ write_file { ... }
  ...

  [Step 3/3] Run pytest to verify the fix
  ⟳ run_terminal { "command": "pytest tests/ -x -q" }
  ...
```

**Agent Loop との違い:**
- 計画はファイル内容を読む前に立てる（高レベルな TODO リスト）
- ステップごとに独立した AgentLoop が動くため、進捗が明確で1ステップが失敗しても次に続ける
- ツールエラーはモデルに返却されるので、自律的に対処できる
- コンテキストはステップ間で継続するため、Step 2 は Step 1 の結果を見ながら動く

**ステップ数の目安（自動決定）:**

| タスク規模 | 典型的なステップ数 |
|---|---|
| 1ファイルの小さな修正 | 1〜2 |
| 複数ファイルにまたがる機能追加 | 3〜5 |
| 大規模リファクタ・新機能 | 5〜10 |

```jsonc
"localLlm.agent.mode": "repo-map-plan"
```

### Repo Map & Plan Loop（PDCA）

`repo-map-plan` を最大 **5 サイクル** 自動ループするモード。ツールエラーが残っている場合、前回の失敗内容と実行履歴をコンテキストに保持したまま再計画します。

**1 サイクルの流れ:**

```
repo map 生成（初回のみ）
  └─ 計画立案 → 承認 → ステップ実行
                              ↓
               エラーなし → Behavior Verify（.py修正時）
                              ├─ PASS → 完了
                              └─ FAIL → 失敗内容を入力に次サイクルへ
               エラーあり / STEP MISMATCH → 次サイクルへ（最大 5 回）
                              ↑
                  前回の実行履歴 + エラー/発見内容をコンテキストに保持
```

- 各サイクルの承認ブロックには `(cycle 2 — fixing errors)` のようにサイクル番号が表示されます
- サイクル 2 以降のモデルは前サイクルのツール呼び出し結果を見ながら再計画するため、同じミスを繰り返しにくい
- 会話履歴はサイクルをまたいで蓄積されるため、直前のやり取りの文脈も引き継ぎます

```jsonc
"localLlm.agent.mode": "repo-map-loop"
```

### Debug（3フェーズ）

バグ調査に特化した構造化エージェント。Agentless (2024) / AutoCodeRover (2024) の研究知見をベースに、単一ループではなく3つの独立したフェーズに分割することで精度を高めます。

**フェーズ構成:**

| フェーズ | 使えるツール | 目標 |
|---|---|---|
| **Phase 1: Localize** | `glob_search`, `grep_search`, `get_file_outline` | 仮説生成→構造確認→`LOCALIZED:` マーカーで箇所を特定 |
| **Phase 2: Repair** | `read_file`, `get_file_outline`, `grep_search`, `edit_file`, `replace_lines`, `write_file` | Phase 1 の箇所を読んで最小修正を適用（`think:false`・トークン予算1.5倍で実行） |
| **Phase 3: Validate** | `run_terminal` のみ | テスト実行→`PASS`/`FAIL` を報告。**FAIL の場合は FAIL 理由を添えて Phase 2 に1回だけ戻る** |
| **Phase 4: Behavior Verify** | （内部実行） | `.py` を修正した場合のみ。下記「Behavior Verify」参照 |

各フェーズは専用の system prompt を持ち、使えるツールが制限されています。「とりあえずファイル全体を読み続ける」ループが発生しない設計です。

### Behavior Verify（LLM生成スモークテスト）

「アプリが起動する」だけでは操作起因のバグ（D&Dが効かない等）は検出できません。Behavior Verify は **LLM 自身に検証をさせる**フェーズです:

1. 修正されたモジュールの全文＋バグ報告から、ハンドラを偽イベントで直接呼ぶスモークテスト（`test_llm_verify_<module>.py`）を生成
2. テストを実行。失敗したら「失敗出力＋ファイル全文＋変更可能関数は1つだけ」という scoped repair を最大2回
3. 最終結果を報告（repo-map-loop では失敗内容が次のPDCAサイクルの再計画入力になる）

- 生成されたテストファイルはワークスペースに残ります（不要なら削除可）
- `localLlm.agent.enableBehaviorVerify: false` で無効化できます
- 対象は現在 Python のみ

**安定性機能（小型ローカルモデル向け）:**

| 機能 | 動作 |
|---|---|
| ループ検知（同一ファイル） | 同じパスの `read_file` が4回を超えると強制ブロック。**ファイルを編集するとカウントはリセット**（変更後の再読は正当なため） |
| 重複編集ブロック | 同一引数の `replace_lines` 等の2回目を即ブロック（行の重複混入を防止） |
| Repair enforcement | `REPAIRED:` マーカーが出ても書き込みツールが未使用なら再試行を強制 |
| 縮退リトライ | 文字列反復・同一行の頻発・自己修正マーカー（3種の検知器）で中断→最大2回リカバリ。中断前の分析の末尾800字は次の試行に引き継がれる |
| ツール結果圧縮 | `read_file` は4000字（省略時は「lines X–Y OMITTED — この範囲を再読せよ」と案内）、`run_terminal` はエラー行を抽出、その他は先頭800+末尾600字 |
| 構文チェック | `.py` への書き込み直後に `py_compile`。壊れたら「ファイル全体を読み直して関数全体を1回で書き換えよ」という回復手順つきで即報告 |
| 親ウィジェット調査誘導 | Phase 2 で修正箇所が見つからない場合、親・兄弟クラスのイベント横取りを確認するよう誘導 |

**向いているタスク:** 「なぜ動かないのか」「このエラーの原因は」「この機能が壊れている」など、根本原因の調査が必要なデバッグ作業。

## 8. 権限モード（Modes）

入力欄左の **モードボタン**（🔒 Ask など）をクリックするとモード選択パネルが開きます。Claude Code と同じ 4 つのモードが使えます。

| モード | ボタン表示 | 動作 |
|---|---|---|
| **Ask** | 🔒 Ask | すべてのファイル操作・ターミナル実行の前に毎回確認ダイアログを表示（デフォルト） |
| **Edit** | ✏ Edit | ファイル編集（`write_file` / `edit_file` / `replace_lines`）は自動許可。ターミナルのみ確認 |
| **Plan** | ≡ Plan | ファイル変更・ターミナルをブロック。代わりに番号付き実行計画を出力 |
| **Auto** | ⚡ Auto | すべての操作を自動許可 |

> セッション開始時は常に **Ask** モードにリセットされます。

> **入力欄のモードボタン:** 入力欄右側の `[🔒 Ask]` ボタンをクリックするとモードパネルが開きます（トークン表示の左隣）。

### 権限確認ダイアログ（Ask / Edit モード）

ファイル編集の場合、変更内容の diff が折り畳みで確認できます：

```
┌──────────────────────────────────────────────┐
│ 🔑 PERMISSION REQUEST                         │
│  Edit: src/main.py                            │
│  ▶ View changes                               │  ← クリックで diff 展開
│    - old_line_1                               │
│    - old_line_2                               │
│    + new_line_1                               │
│    + new_line_2                               │
│  [Yes (once)]  [Always Yes (session)]  [No]  │
└──────────────────────────────────────────────┘
```

| ボタン | 動作 |
|---|---|
| **Yes (once)** | 今回の操作のみ許可 |
| **Always Yes (session)** | このセッション中はすべて許可（以降確認なし） |
| **No** | 拒否（LLM は再試行しません） |

> **注意:** `/new` や `+` で新しいセッションを開始すると、モードと許可状態はリセットされます。

### 計画承認ブロック（repo-map-plan / repo-map-loop）

`repo-map-plan` と `repo-map-loop` モードでは、実行前にチャット内インラインで計画承認ブロックが表示されます。計画が準備できると **VS Code のポップアップ通知**も表示されるため、パネルからフォーカスが離れていても気付けます。

| ボタン | 動作 |
|---|---|
| **Approve** | 計画を承認して実行開始 |
| **Cancel** | 計画を中断（エージェントは停止） |

通知の **Approve** / **Cancel** ボタンをクリックしても同様に動作します。

`repo-map-loop` では、エラー修正サイクルごとに新しい承認ブロックが表示されます。

## 9. 思考過程の表示（Thinking）

DeepSeek-R1、Qwen3、Gemma4 などの推論モデルは、回答の前に内部推論を出力します。

この拡張は思考過程を**折り畳み表示**します：

```
▶ Thinking…     ← クリックで展開
```

展開するとモデルの推論ステップが表示されます。デフォルトは折り畳み状態です。

**対応している思考形式:**

| モデル系統 | 思考出力方式 |
|---|---|
| DeepSeek-R1 | `<think>…</think>` タグをコンテンツ内に埋め込む |
| Qwen3（`qwen3.*`） | Ollama の `think: true` オプション経由で有効化。コンテンツ内に `<think>` タグとして出力される |
| Gemma4 | Ollama の `thinking` フィールドとして分離して送信（自動でラップ） |

**thinking が表示される場面・されない場面:**

| 場面 | thinking |
|---|---|
| standard（Agent Loop）/ chat / ReAct / Debug の Localize・Validate | 表示される |
| プラン生成 / プランのステップ実行 / Debug の Repair / Behavior Verify | **表示されない（意図的に `think:false` で実行）** |

repair 型の作業で thinking を有効にすると、トークン予算を自己修正ループに全消費して出力ゼロで終わる失敗が実測で確認されているため、これらの場面では無効化しています。バグではありません。

**重要:** `<think>` の内容はモデルの推論トークンであり、会話履歴（contextManager）には保存されません。次のターンでモデルが自分の思考トークンを読み返して推論ループを起こすのを防ぐためです。

> **Gemma4 に関する注意:** Gemma4 はシステムプロンプトの指示をある程度無視して応答内に推論ステップを出力することがあります。完全には防げない挙動です。

## 18. Web 検索

`web_search` ツールは DuckDuckGo を使用します（API キー不要）。日本語クエリにも対応しています。

### 検索フロー

1. **Instant Answer API:** 実答（AbstractText）がある場合のみ採用（百科事典的な曖昧さ回避だけの応答では実検索へフォールバック）
2. **HTML 検索:** ニュース・日本語クエリなど、実際の Web 検索結果（タイトル＋スニペット＋URL）を取得
3. **`fetch_url`:** 検索結果のページ本文を取得（JSON APIにも対応）

### 時事系クエリのための仕組み

- システムプロンプトに**現在日時**が注入され、「明日」「今日」は絶対日付に解決してから検索されます

- auto モードでは「天気/ニュース/最新/今日/明日」等を含む質問はツールなしの Chat モードに振られず、必ずツール付きエージェントが担当します

```
「東京 明日の天気」
「requests ライブラリの最新バージョンは？」
「TypeError: cannot read property of undefined 解決方法」
```

## 20. トラブルシューティング

### ステータスバーが `Disconnected` のまま

1. `ollama serve` が起動しているか確認
2. 設定の接続ポートを確認（デフォルト: `11434`）

### LLM がツールを使わず説明文だけ返す

- ツール対応モデルを使用しているか確認（`qwen2.5-coder`, `llama3`, `gemma4` 等を推奨）
- モデルが tool calling をサポートしていない場合は `localLlm.agent.framework: "react"` を試してください

### LLM が同じファイルを何度も読み取る

Agent Loop には3層のループ検知が組み込まれています。

| 検知方式 | トリガー | 動作 |
|---|---|---|
| **フィンガープリント** | 同じツール+引数が3回 | 実行をスキップして強制リダイレクトメッセージを返す |
| **ファイルパスレベル** | 同一パスへの `read_file` が4回超 | 「既にコンテキスト内にある」ブロックを返す。**ファイルを編集するとカウントはリセット**される（編集後の再読は正当） |
| **重複編集** | 同一引数の書き込みツール2回目 | 実行をブロック（同じ行の重複混入を防止） |

いずれもモデルに「別のアクションを取るよう」促します。読みすぎ・書きすぎの両方向をカバーします。

それでも改善しない場合は:
- **Debug モード**に切り替えてください。Phase 1（Localize）では `get_file_outline` と `grep_search` のみ使用可能なため、全文読み込みループが構造的に発生しません。
- `/compact` でコンテキストを圧縮する（コンテキストが溢れて混乱している可能性）。

### Windows でターミナルコマンドの出力が文字化けする

ターミナルツールは PowerShell 実行時に UTF-8 出力を強制するため、通常は問題ありません。それでも文字化けが起きる場合は、プロンプトで「出力を英語で表示して」と指示してみてください。

### Windows でターミナルコマンドがエラーになる

ターミナルツールは **PowerShell** で実行されます。LLM が bash コマンド（`ls -R` 等）を使う場合は失敗します。システムプロンプトで PowerShell コマンドを使うよう強く指示されていますが、依然として bash 構文を使う場合はプロンプトで「PowerShell コマンドを使って」と明示してください。

### ターミナルが 30秒でタイムアウトする

長時間かかるコマンドは `timeout_seconds` パラメータで最大 120 秒まで延長できます。

### エージェントが「タイムアウトしました」と返す

Ollama へのリクエストにはタイムアウトが設定されています：
- **ストリーミング（通常の回答生成）:** 10分
- **非ストリーミング（コンテキスト圧縮等）:** 2分

10分を超えるような超長文生成が必要な場合は、タスクを小さく分割してください。

### `web_search` が `(no results)` を返す

クエリをより具体的にするか、英語で試してください。

### LLM が同じコマンドを繰り返す

Agent Loop のループ検知が3回目で自動介入します。それ以上続く場合は **⏹ Stop** で停止し、「先ほどのコマンドは失敗しました。別の方法で試してください」と伝えてください。

### エージェントがループし続ける

**⏹ Stop** ボタンで強制停止。停止後は UI が即座に通常状態に戻ります。バグ調査で繰り返しが多い場合は **Debug モード**への切り替えも検討してください。

### ファイルを編集させたいのに変更されない

権限確認ダイアログで **Yes** を選択してください。同一セッション中に確認を省略したい場合は **Always Yes (session)** を選ぶと以降は自動承認されます。

### セッションを誤って閉じてしまった

**⏱ ボタン** → 履歴パネルから **Load** で復元できます（最大 20 件保持）。

### repo-map-plan が「Could not generate a valid plan」と表示される

モデルが有効な JSON を最大 3 回の自動リトライ後も返せなかった場合に表示されます。各リトライではモデルに「前回の応答が無効な JSON だった」と伝えるフィードバックが送られます。

- Qwen3 や Gemma4 など思考トークンを出力するモデルは自動でトークンが除去され、JSON 部分のみ抽出されます
- タスクの説明をより具体的にするとプランの品質が上がります
- より高性能なモデルに切り替えてから再試行してください

### repo-map-loop がサイクル 5 で停止した

最大 5 サイクル繰り返してもエラーが解消されなかった場合に停止します。Agent Loop モード（通常のエージェントループ）に切り替えて、残った問題を対話的に解決してください。

### アクティブファイルが入力欄に表示されない

エディターでファイルを開いた後、ファイル名が入力欄の `／` ボタン右隣に表示されます。ファイルを開いていない場合や、ファイル名が表示されない場合は、一度エディターでファイルをクリックしてフォーカスを当ててください。

### アクティブファイルをコンテキストから除外したい

アクティブファイルチップの左端にある **書類アイコン** をクリックすると、目に斜線が入りコンテキストから除外されます。もう一度クリックすると元に戻ります。

### repo-map モードで完了後にサマリーが表示されない

AgentLoop がすべてのツール呼び出しを完了した後、モデルが自動的にサマリーを出力します。実行メッセージに「After completing all steps, provide a concise summary...」の指示が含まれているため、正常に動作していれば最後に日本語または英語のサマリーが表示されます。表示されない場合はモデルの応答品質の問題なので、より高性能なモデルに切り替えるか、タスクの説明に「完了後に何をしたか報告してください」と明示してください。

### ツール実行中のスピナーが消えない

各ツール呼び出しブロックの左端に表示される小さなリングスピナーは、ツール結果が届いた時点で自動的に消えます。スピナーが残っている場合は、そのツールがまだ実行中か、応答待ちの状態です。長時間続く場合は **⏹ Stop** で停止してください。
